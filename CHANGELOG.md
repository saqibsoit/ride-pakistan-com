### Added
- Milestone 10a admin catalogue and schedule control:
  - Order snapshot: orders keep the product name, type, sessions and validity they were bought with (new `orders.product_*` columns, backfilled). `FulfilOrder` grants credits and expiry from the order, so a package edited while its bank transfer waits keeps the terms bought. Stripe line items, receipts, emails, tickets, the data export and admin order screens show the name as bought. A product's type is fixed once it has orders.
  - Archive instead of delete: `ArchiveProduct` / `RestoreProduct` (`products.archived_at`); archived products leave the site, the booking flow and the admin list's default view, and are read-only until restored (off sale). Only products nobody ordered can be deleted (`DeleteProduct`); the Delete button appears only then. Bulk delete is off.

- Milestone 6 Stripe Checkout and webhooks (PKR):
  - `php artisan stripe:check`: creates and expires a PKR 10,000 test Checkout Session to confirm the account supports PKR (test keys only). Stripe calls go through `StripeGateway`. Tests bind an in-memory fake that still verifies signatures with stripe-php.
  - `/checkout/{reference}`: "Pay by card" and "Pay by bank transfer" (the transfer flow opens in milestone 7), with a note that some Pakistani cards block international online payments. `CreateStripeCheckout` builds a PKR session from the order's own items (client reference, metadata, customer email, status-page return URLs, statement descriptor suffix, "Ride Pakistan by Destination Pakistan" on the Stripe page). It extends the seat hold to match the session (Stripe's 30-minute minimum), reuses an open session, and uses one idempotency key per attempt. Rate limited.
  - `POST /webhooks/stripe`: signature verified (400 otherwise), no session or CSRF, rate limited, idempotent on the event id (`stripe_events`), one transaction (500 and a full rollback on failure, so Stripe retries). Paid sessions are checked for reference, amount and currency, then fulfilled by `FulfilOrder` only. Mismatches are never fulfilled and raise an alert (critical log, audit entry, "Needs review" flag). Payments that can no longer be fulfilled are refunded automatically. Failed or expired sessions keep the order and its seats until the hold ends, so the customer can retry by card or pay by transfer under the same reference.
  - `holds:release` expires a card order's open Stripe session before expiring the order, and leaves orders Stripe reports as paid to the webhook.
  - `/checkout/{reference}/status`: Livewire, polls every 3 s for up to 2 minutes, read-only.
  - Receipt email "Payment received" (queued after commit via `OrderPaid`) with the sessions, tickets and pack validity.
  - Admin refunds (Orders → View → Refund): full or partial through the Stripe API, reason required. A full refund cancels upcoming bookings and voids unused credits (pack revoked); a partial one applies the bookings and credits the admin picks (`CreditPacks::remove`, ledger "adjusted"). `charge.refunded` records dashboard refunds and flags the order. Orders list: "Needs review" column and filter, and a "Mark reviewed" action.
  - `config/csp.php`: Stripe Checkout `form-action` entry. README: Stripe CLI setup and a manual test script.
  - Pest tests: valid, invalid, missing, stale and tampered signatures; duplicate events; amount, currency and reference mismatches; async success and failure; expired sessions and hold release; automatic refunds; rollback and retry; checkout parameters, hold extension, session reuse, ownership, rate limits; status polling and its time limit; full, partial, repeated, over and failed refunds; dashboard refund reconciliation; admin actions; the receipt; `stripe:check`.
- Milestone 5 booking engine, holds, packages and credits:
  - Overbooking guard: every hold or booking write takes a `SELECT … FOR UPDATE` lock on the slot row, then counts its bookings and active holds with locking reads (`SlotLock`). Order creation takes the lock before inserting anything, so foreign-key checks can't deadlock two orders. Proven by a parallel test against MariaDB: separate PHP processes race for the last seat (2 and 10 contenders, exactly one wins), a private and a group booking race for an empty slot, and a hold blocked on the row lock refuses once the seat is taken meanwhile.
  - Private sessions take the whole slot and keep blocking it after payment (`is_private` on holds and bookings). Rule and manual slots are bookable alike, until they start (new setting `booking.min_notice_hours` [0]).
  - `CreateOrder` prices from the product row only (`PriceQuote`, re-read from the database; a tampered model or Livewire payload changes nothing), holds seats for `booking.card_hold_minutes` [30] and returns the same order on a double submit. `holds:release` (every minute) expires unpaid card orders and frees seats.
  - `FulfilOrder` (idempotent; for the Stripe webhook and bank transfer approval): paid through `OrderStateMachine`, holds turned into bookings with unique 12-character ticket codes, a credit pack for packages (valid from payment) with granted/used ledger entries, and a re-check if a hold ran out before payment.
  - Credits: one pack per account usable by any of the customer's riders (`BookWithCredit`, soonest-expiring pack first, group sessions only, session must start before the pack expires). `CancelBooking` returns the credit before the cutoff and not after; `RescheduleBooking` moves credit bookings before the cutoff (private sessions move as a group). `credits:expire` (daily) writes off unused credits.
  - `/book`: Livewire flow (product, date, riders, review) with live seats, guest rider details and sign-in by code that resumes the booking, and "use my credits". `/checkout/{reference}` shows the order and how long seats are held (payment methods come in milestones 6 and 7).
  - Live data on public pages: `/schedule` (live slots with seats left and Selling fast, All / Group / Private filters), the home page "This weekend" strip, and a booking widget on product pages (plain form, next slots, rider stepper). The full-page cache is cleared after any seat change.
  - Account: move or cancel credit bookings (paid bookings say "contact us"); "Book a session with credits" from `/account/credits`.
  - Admin: Bookings list with attended, no-show, move and cancel (reason required); manual bookings with a credit or no charge; the same tools on a slot's bookings tab; Extend on a customer's credit packs.
  - Livewire pages load Livewire's bundled Alpine through a second Vite entry (`resources/js/livewire.js`, Livewire's auto-injection off); plain pages keep `app.js`. This also fixes the riders page, which loaded Alpine twice.

Livewire's automatic asset injection is off (since milestone 2, for the public bundle), so in a real browser the panel's Livewire and Alpine never started and forms such as the login spun forever. Tests render HTML only, so they missed it; a regression test now checks for the script.
- The private `local` disk no longer registers the framework's `GET`/`PUT /storage/{path}` signed-URL routes (`serve` off; nothing used them).
- The full-page cache now has its own cache store. It used the default store, and `ResponseCache::clear()` (run after every seat change and content edit) emptied that whole store, resetting rate-limit counters, including the sign-in code limits. A regression test covers it.

### Changed
- npm devDependencies pinned to exact versions; `alpinejs` replaced by `@alpinejs/csp` 3.17.5 (milestone 10).
- Leads and lead notes are no longer admin-only: staff can view, add, move, assign and note them (milestone 9). Converting, deleting and the lead reports stay admin-only.
- Removed unconfirmed claims that could be wrong or unsafe: helmet provision and requirements, arrival time, weather rescheduling, consent for minors, photography, transport, the "Is horse riding safe for beginners?" FAQ, reply-time promises, "Most popular", "multi-day" expeditions and package outcome claims. Riding rules and booking policies now default to confirmed or neutral wording only.
- Group size is derived from the riders-per-slot setting instead of a hard-coded "Up to 6 riders".
- Prices follow PLAN §2 (8-class PKR 60,000, 16-class PKR 100,000), not the reference page's older rows. Bank details no longer appear on public pages; they move to the checkout transfer page (milestone 7).
- Test runs use a 512 MB memory limit (`phpunit.xml`) for the larger suite.
- Stack pinned to PHP 8.3 + Laravel 12 instead of Laravel 13 (see `docs/PLAN.md` §4).
- Test suite runs on MariaDB (`ride_pakistan_testing`) instead of SQLite, locally and in CI (MariaDB 11.8 service). `TestCase` refuses to boot unless the database name ends in `_testing`; Feature tests use `RefreshDatabase`.
